# Observations

Source: scripted-model execution + span trees + reading installed library behavior. Items needing a real model are marked **[live pending]**.

## Agent fundamentals
1. **Agent vs LLM call**: an LLM call maps input → output once. Here the model's output (a tool request) triggers an action whose result is fed back and may trigger another — a feedback loop (S2 needs 3 model calls).
2. **Autonomy**: the model chooses whether/which tool and when to stop; code only enforces a budget (`MAX_STEPS=8`).
3. **Control loop**: LangGraph — explicit graph cycle `agent`↔`tools` (our code). Pydantic AI — inside `Agent.run` (library).
4. **Who decides next action**: the LLM, every iteration.

## Tools
5. **Selection**: model picks from the tool schemas sent with each request. **[live pending]** for real selection quality.
6. **Arguments**: generated by the model as JSON matching the schema.
7. **Validation**: pydantic, inside each framework's tool wrapper (observed for `b="hello"`).
8. **Execution**: the framework, in our process (LangGraph `ToolNode`; Pydantic AI tool manager). Model never executes.

## State
9. **Stored**: LangGraph — `MessagesState["messages"]` in graph state (explicit). Pydantic AI — run's message history (implicit; `all_messages()`).
10. **Passed between iterations**: full message list, including tool results; the model is stateless.
11. **Between requests**: nothing — each `run()` starts fresh (no checkpointer/memory configured). Persisting needs LangGraph checkpointer or passing `message_history` in Pydantic AI (Phase 2+).

## Failures (see failure-analysis.md)
12. Tool throws: LangGraph feeds it back and continues; Pydantic AI aborts the run.
13. Invalid args: both feed a validation error back; Pydantic AI counts retries.
14. Retry: only Pydantic AI has an explicit counter (tool-level). In LangGraph "retry" is just the model trying again until the step cap.
15. Control of retry: Pydantic AI `retries=`/`ModelRetry`; LangGraph `handle_tool_errors`, recursion_limit.

## Observability
16. **Trajectory reconstructable**: yes in the span trees — alternating LLM and TOOL spans in order (LangGraph 14 spans, Pydantic AI 6 spans for S2). Message payload attributes and Langfuse rendering **[live pending]**.
17. **Failing step**: tool span has status ERROR in both; Pydantic AI also marks the root span ERROR when the run aborts, LangGraph root stays OK when the error is handled.
18. **Correlating LLM and tool**: by parent/child and ordering within one trace (1 trace per run in both). Tool-call-id linkage in attributes **[not inspected]**.

## Architecture
19. **Framework-specific**: how errors default, retry counters, state shape, span granularity, test helpers.
20. **Fundamental**: model emits structured action → code executes → result appended → model called again; stop when no action; guard with a budget; handle errors by policy.

## Surprises
- Pydantic AI v2.62 reports retried tool calls as `ToolReturnPart(outcome="retried")` rather than `RetryPromptPart` — my first extractor was wrong until run.
- LangGraph's source for the default handler suggests only `ToolInvocationError` is handled, yet `ZeroDivisionError` was fed back — observed behavior beats reading; the installed code path was not traced further.
- LangChain's instrumentor produced extra `tools_condition` CHAIN spans (routing is visible as a span).
